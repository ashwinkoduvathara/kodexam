# 05 — Screen 1: System Check

**Route:** `/exam/:examId/system-check`
**Main component:** [`SystemCheck.tsx`](../src/components/exam/system-check/SystemCheck.tsx)

The candidate must pass the camera, microphone, speaker and internet checks before continuing.
Which checks are required comes from the server (`session.requiredChecks`).

## Check states

All checks share one status type ([`types.ts`](../src/lib/exam/types.ts)):

```ts
type SystemCheckStatus = "idle" | "checking" | "passed" | "warning" | "failed" | "not_available";
```

A machine-readable `reason` explains why a check isn't passing (`permission_required`, `no_device`, `device_error`, `disconnected`, `timeout`, `no_input`, `not_heard`, `connection_lost`, …). The candidate always sees a friendly message, never a raw browser error.

## Camera — [`use-camera-check.ts`](../src/hooks/use-camera-check.ts)

- Calls `navigator.mediaDevices.getUserMedia()` and shows the live, mirrored preview.
- **Passes only after a real video frame renders** (`requestVideoFrameCallback`, with a fallback). A resolved `getUserMedia()` alone isn't enough.
- **Timeout:** fails if no frame arrives within 10 seconds (counted only while the tab is visible).
- **Stall watchdog:** a passed camera that stops producing frames for 4 seconds fails again.
- **Change Camera:** lists devices after permission. Switching stops the old stream, opens the new device and verifies it.
- Handles disconnection (track `ended`) and recovers automatically when a camera is plugged back in.
- **Lighting:** genuinely measured from frame brightness.
- **Face in frame / face visible:** need a face detector, so they show *"will be verified during Identity Verification"*. The detection interface is ready for an ML provider to be plugged in.

| Browser error | Candidate sees |
|---|---|
| `NotAllowedError` | **Permission Required** — "Camera access is blocked. Allow camera access from your browser settings and try again." |
| `NotFoundError` | **No Camera** — "No camera was detected. Connect a camera and try again." |
| `NotReadableError` | **Device Error** — "The camera is currently being used by another application." |
| `SecurityError` | **Not Supported** — "Camera access is unavailable in this browser environment." |

## Microphone — [`use-microphone-check.ts`](../src/hooks/use-microphone-check.ts)

- `getUserMedia()` → `AudioContext` → `AnalyserNode`, shown as a live **12-bar meter**.
- **Passes only after usable input:** at least 400ms of signal above −42 dB, added up across bursts of speech.
- **No Input:** if the mic delivers digital silence or is muted for 6 seconds.
- If the browser starts the audio engine suspended, the meter asks the candidate to click anywhere to activate it.
- Supports switching microphones, permission handling and disconnect recovery.

## Speaker — [`use-speaker-check.ts`](../src/hooks/use-speaker-check.ts)

- Plays a three-note chime generated by Web Audio, with a volume slider.
- The candidate must answer **"Did you hear the test sound?"** with *Yes, I heard it* or *No, try again*. It never passes on its own.
- If the audio output device changes after passing, it asks for a retest.

## Internet — [`use-network-check.ts`](../src/hooks/use-network-check.ts)

- Shows status, latency, download and upload, through the replaceable `NetworkTester` interface ([`network-test.ts`](../src/lib/exam/network-test.ts)).
- Going **offline** immediately shows **Connection Lost**. Coming back online re-runs the test.
- A heartbeat every 10 seconds catches "Wi-Fi connected but no internet".
- Against localhost or a private network, speeds would be meaningless, so it shows **"Speed test unavailable"** and still measures latency.
- **Thresholds:** fail below 1.5 Mbps down / 1 Mbps up or above 400 ms latency; warn below 5 / 2 Mbps or above 150 ms.

## Readiness engine — [`use-system-readiness.ts`](../src/hooks/use-system-readiness.ts)

- One central store holds every check's state.
- `allRequiredChecksPassed` is derived once and drives the Continue button.
- [`validateSystemReadiness()`](../src/lib/exam/readiness.ts) is the **final authority**. It probes the real resources: live video track producing frames, mic analysis running, speaker confirmed, and the exam server answering a ping. It runs when everything passes, every 5 seconds while Continue is enabled, and again on click.
- If any check fails later (for example the internet drops), Continue is disabled immediately.

## Continue

Continue runs this sequence:

1. Re-validate the devices.
2. `POST /api/exam-attempts/:attemptId/system-check` with the results. The server checks that the required ones passed.
3. Status becomes `INSTRUCTIONS`.
4. Navigate to Screen 2.

## Media cleanup — [`media-registry.ts`](../src/lib/exam/media-registry.ts)

Every stream and `AudioContext` is registered and released:

- when a component unmounts
- when the route is left (route `onLeave`)
- when the page is closed (`pagehide`)
- when the session expires

Nothing is recorded or uploaded. The camera preview and audio analysis stay on the device.

## Other features

- **Permissions API:** used where the browser supports it. Granting permission in browser settings re-runs the check automatically.
- **Support dialog:** email, phone, hours and the attempt reference.
- **Privacy note:** *"Camera and microphone access is used only for exam verification and proctoring…"*
- **Accessibility:** one screen-reader announcement region for status changes, keyboard operation and ARIA labels.
- **Fullscreen helper:** [`fullscreen.ts`](../src/lib/exam/fullscreen.ts) and [`use-fullscreen.ts`](../src/hooks/use-fullscreen.ts) are ready for Screen 4. Not enforced here.
